# Insights Webapp Constitution

`insights-webapp` is the Weni Insights dashboard: a Vue 3 microfrontend built
with Rspack and exposed through Module Federation (`name: 'insights'`) to the
Connect host, while remaining runnable standalone. This constitution is the
synthesis of the VTEX CX engineering base, the frontend base, and the frontend
platform base, applied to this repository.

## Core Principles

### I. Reviewed Changes on a Protected Main Branch

All code MUST enter `main` through a pull request on `weni-ai/insights-webapp`.
A merge MUST require at least one approved review and a green CI run. Direct
pushes to `main` MUST be blocked via GitHub branch protection.

In this repository, reviewers are requested automatically through
`.github/CODEOWNERS`, and "green CI" means the `Run Coverage, Lint Files and
Build Project` workflow (`.github/workflows/test-and-build.yml`) passed for the
PR's head commit. PR descriptions SHOULD follow
`.github/pull_request_template.md` (Type of Change, Why, What Changed).

**Rationale:** the policy is only real when enforced by the platform, not by
trust. Peer review and a protected main branch keep history auditable and
prevent unreviewed changes from reaching production.

### II. Security and Secrets

Secrets MUST never be committed to the repository. Secrets MUST be provided by
an external secrets manager and injected at runtime. Access MUST follow least
privilege by default. Dependencies MUST come only from trusted sources and MUST
be checked for known vulnerabilities.

In this repository:

- `.env` is git-ignored; `.env.local.sample` MUST contain only key names with
  empty values.
- Runtime configuration is injected into `index.html` at container start by
  `docker-entrypoint.sh`; CI and deploy credentials come from GitHub Actions
  secrets (`secrets: inherit` in the build workflow).
- Every value delivered to the browser is public. Only public client
  identifiers (e.g., Firebase web config, Sentry DSN) MAY be injected into the
  bundle or runtime config; credentials that grant privileged access MUST NOT
  reach the client.
- Dependencies MUST be installed from the npm registry through the committed
  `package-lock.json` (`npm ci` in CI).

**Rationale:** leaked credentials and untrusted dependencies are among the most
common and most damaging breaches; prevention is far cheaper than remediation.

### III. Observability

Logs MUST be structured and MUST never contain secrets or sensitive personal
data. Errors MUST be traceable across components through correlation or trace
identifiers.

In this repository, Sentry is the error-reporting channel: `@sentry/vue` is
initialized in `src/main.js` with `browserTracingIntegration({ router })` and
session replay, and `src/utils/moduleFederation.js` reports remote-load
failures through `@sentry/browser`. Captured errors MUST carry context as
structured `tags` / `extra` fields rather than interpolated strings. Sentry
events, breadcrumbs, and replays MUST NOT include auth tokens or personal data.
`console.*` output is a development aid, not the observability channel.

**Rationale:** structured, privacy-safe telemetry is what makes incidents
diagnosable without creating new data-exposure risks.

### IV. Versioned Contracts

Any change to a public interface MUST be versioned following SemVer. Changes
MUST be backward compatible or ship with an announced deprecation path. Silent
breaking changes MUST NOT be introduced.

The public interfaces of this repository are the Module Federation exposes
declared in `rspack.config.mjs`:

- `./main`: the `mountInsightsApp({ containerId, initialRoute })` entry point
  and its returned `{ app, router }`
- `./dashboard-commerce`: the `DashboardCommerce.vue` component and its props
- `./locales/pt_br`, `./locales/en`, `./locales/es`: the exposed locale
  bundles and their keys as consumed by the host

The host contract consumed from Connect (`connect/sharedStore`) is governed by
Connect's versioning; changes in how this repository reads it MUST stay
compatible with the host versions in production. Release tags MUST follow
SemVer (`X.Y.Z`, `X.Y.Z-staging`, `X.Y.Z-develop`), and a breaking change to
an expose MUST bump MAJOR and be coordinated with the host.

**Project exception (no changelog):** this repository does not maintain a
changelog. The base Changelog Maintenance article targets public libraries,
and `insights-webapp` is a deployable application, not a published package.
Release history is tracked through SemVer release tags and the pull requests
merged into `main`.

**Rationale:** consumers depend on stable contracts; explicit versioning and
deprecation give them a predictable path to adapt without outages.

### V. Specification Traceability

Every engineering spec MUST derive from exactly one approved product spec and
MUST reference it through an immutable, pinned version (commit or tag). A
mutable URL or ID alone MUST NOT be used. The product spec MUST exist and be
tagged before its engineering spec is created. An engineering spec MUST NOT
redefine the "what" it inherits: problem, scope, success criteria, and binding
decisions belong to the product spec. A technical architecture document SHOULD
be produced for non-trivial features; when it exists it MUST be linked from the
engineering spec, also pinned by commit or tag, but its absence MUST NOT block
the engineering spec.

Engineering specs in this repository live in `specs/<NNN-feature>/spec.md`
(sequential numbering). Every engineering spec MUST open with an inheritance
section in exactly this format:

```
## Inheritance from Product Spec
- Product Spec: <title> — <URL>
- Pinned version: <commit/tag>
- Architecture doc: <none | URL + commit/tag>
- Inherited binding decisions: <short list>
- Scope of this spec: <slice implemented by this repo>
- Divergences: <none | link to amendment>
```

The current `.specify/templates/spec-template.md` does not contain this
section; authors MUST add it at the top of each `spec.md` until the template
is updated (see TODO(SPEC_TEMPLATE) and TODO(PRODUCT_SPEC_REPO)).

**Rationale:** traceability from product intent to technical execution keeps
decisions auditable. Pinning the version guarantees every team implements the
same version of the feature instead of divergent readings of a spec that
changed mid-flight. A mandatory product spec prevents engineering work without
an agreed problem; an optional architecture doc avoids blocking delivery on
ceremony when the design is trivial. A single inheritance format keeps the
link machine-checkable and uniform across repositories.

### VI. No Silent Divergence

When a technical need contradicts something inherited from the product spec
(scope, success criteria, or a binding decision), the divergence MUST NOT be
implemented silently in code. It MUST be raised as an amendment in the product
repository and recorded in the `Divergences` field of the engineering spec's
inheritance section, linking to that amendment. Once the amendment is approved
and produces a new tag, the engineering spec's `Pinned version` MUST be
updated to it. A technical difference that contradicts nothing inherited is
not a divergence but an implementation decision, and MUST live in the
engineering spec.

**Rationale:** with the product spec as the single source of truth, a silent
code deviation makes intent and implementation drift apart with no audit
trail. Forcing divergences through amendments keeps the spec authoritative and
every decision traceable to an agreed change.

### VII. Conventional, Atomic Commits

Commits MUST follow the Conventional Commits format `<type>: <description>`.
Allowed types are `feat`, `fix`, `docs`, `refactor`, `test`, and `chore`. The
description MUST be imperative, specific, and no longer than 50 characters.
Commits MUST be atomic: one logical change per commit.

**Rationale:** conventional commits make the history scannable by type and
support semantic versioning of releases. Atomic commits simplify bisecting, reverting, and
reviewing.

### VIII. Linting and Formatting

All code MUST pass the project's ESLint configuration without errors before
merge. The configuration MUST extend `@weni/eslint-config`
(https://github.com/weni-ai/eslint-config). Formatting MUST be enforced through
the configured tooling; style debates MUST NOT occur in code review.

In this repository, `.eslintrc.cjs` extends `@weni/eslint-config/vue3` with
`@typescript-eslint/parser`, Prettier runs through `eslint-plugin-prettier`,
and CI runs `npm run lint`. Because that script passes `--fix`, the CI gate
does not currently fail on auto-fixable violations (see TODO(CI_LINT_GATE)).

**Rationale:** a shared ESLint configuration ensures consistency across all
frontend projects. Automated enforcement eliminates subjective discussions and
guarantees a uniform codebase.

### IX. Code as Documentation

All code MUST be written entirely in English, including variable names,
function names, comments, and documentation. Domain-specific terms or acronyms
that only have meaning in their original language MAY remain untranslated
(e.g., `CSAT`, `CTWA`). Code MUST prioritize readability and clarity over
brevity. Every non-trivial decision MUST be documented through comments that
explain the "why", not the "what".

**Rationale:** a globally comprehensible codebase enables open-source
contribution and cross-team collaboration. Clear code reduces onboarding time
and maintenance cost, and comments that explain reasoning stop future
developers from breaking invariants they cannot see.

### X. Type Safety

All new files MUST be written in TypeScript: `.ts` modules and Vue SFCs with
`<script setup lang="ts">`. JavaScript files SHOULD only be modified for bug
fixes or small changes; substantial modifications SHOULD include migration to
TypeScript. Type definitions MUST be explicit; `any` SHOULD be avoided except
when interfacing with untyped external libraries. Strict mode MUST be enabled
in the TypeScript configuration.

Current state: `src/` has 92 `.ts` files and 338 `.js` files, and 209 of 231
SFCs use `lang="ts"`. Only `jsconfig.json` exists, so strict mode is not
enabled and CI runs no type check (see TODO(TS_STRICT)). Shared declarations
live in `types/` and `src/models/types/`.

**Rationale:** static typing catches errors at compile time, improves tooling,
and serves as inline documentation. Gradual migration allows incremental
adoption without blocking delivery.

### XI. Single Responsibility

Each file SHOULD contain no more than 350 lines of code. Each function MUST
have only one responsibility. Template logic MUST be extracted to computed
properties or methods to keep markup clean and declarative. Complex
conditional rendering MUST be abstracted into descriptive boolean variables.

**Rationale:** small, focused units are easier to test, review, and refactor.
Large files and multi-purpose functions create cognitive overload and hide
bugs. Readable templates make a component's visual structure immediately
apparent.

### XII. Naming Conventions

Variable and function names MUST use `camelCase`. Component names MUST use
`PascalCase`. File and directory names MUST be lowercase; multi-word names
SHOULD be joined with hyphens (e.g., `metric-goals.ts`). Abbreviations MUST be
avoided unless universally understood; clarity MUST take precedence over
conciseness.

**Project exception (Vue SFCs and composables):**

- Vue single-file component files MUST be named in PascalCase matching the
  component name (e.g., `CardVtexOrder.vue`). A folder that holds a component
  and its subcomponents MUST share that component's PascalCase name (e.g.,
  `CsatRatings/CsatRatings.vue`).
- Test files MUST mirror the name of the unit under test (e.g.,
  `__tests__/CsatRatings.spec.js`).
- Composable files MUST keep the Vue `use` prefix in camelCase (e.g.,
  `useDateTime.ts`).
- All other files and directories follow the lowercase rule above. Existing
  camelCase files and folders outside this exception (e.g.,
  `src/utils/hostSharedStore.js`, `src/store/modules/humanSupport/`) are
  legacy and SHOULD be renamed when substantially modified.

Justification: the Vue style guide recommends PascalCase SFC filenames so that
the file, the import, the template tag, and the devtools label share one name.
221 of 231 SFCs and 36 component folders already follow it, and `useX` is the
Vue ecosystem convention for composables. Forcing lowercase would split the
codebase into two conventions without improving searchability.

**Rationale:** consistent naming reduces cognitive load and makes the codebase
searchable. Predictable file naming enables automated tooling and faster
navigation.

### XIII. Component Architecture

Components MUST be named descriptively and reflect their purpose. Related
components SHOULD be grouped in folders or subfolders (in this repository,
under `src/components/insights/<feature>/`). Component prefixes SHOULD indicate
scope or nature (e.g., `AppHeader`, `UserProfile`). Props MUST have
descriptive names (e.g., `userName`, `userEmail`). Events MUST be prefixed
with `on` (e.g., `onUserEmailChange`, `onUserPermissionsUpdate`). Methods that
handle state updates SHOULD be prefixed with `handle` (e.g.,
`handleUserPermissions`). State variables MUST clearly reflect what they
represent (e.g., `isLoadingUser`, `errorStatusUser`).

**Rationale:** a predictable component structure keeps the codebase navigable.
Clear naming for props, events, and state reduces integration errors and makes
component interfaces self-documenting.

### XIV. Semantic HTML and Accessibility

HTML MUST use semantic elements (`header`, `nav`, `main`, `section`,
`article`, `aside`, `footer`) wherever they apply. Non-semantic containers
(`div`, `span`) MUST only be used when no semantic alternative exists. Heading
tags (`h1`–`h6`) MUST follow a logical hierarchy; every page MUST have exactly
one `h1`. Elements SHOULD have at least one class describing their purpose,
even when no styling is applied.

Interactive elements MUST be keyboard accessible. Form inputs MUST have
associated labels. Color MUST NOT be the only means of conveying information,
which matters in this repository for charts, status badges, and metric-goal
thresholds. Images MUST have meaningful `alt` text or be marked decorative
with `alt=""`. Focus states MUST be visible.

**Rationale:** semantic markup improves assistive-technology support and makes
the markup self-documenting; heading hierarchy is critical for screen-reader
navigation. Accessibility is a legal requirement in many jurisdictions and
improves usability for all users.

### XV. Unnnic Design System

UI primitives MUST be sourced from the Unnnic design system
(`@weni/unnnic-system`, registered in `src/utils/plugins/UnnnicSystem.js`) when
available. Custom components MUST NOT duplicate design system functionality.
Design system updates MUST be adopted through controlled version upgrades in
`package.json`, not copy-pasted code. For component references, props, tokens,
and usage patterns, the Unnnic skill MUST be consulted.

Legacy components MUST NOT be introduced in new code when modern alternatives
exist; the Unnnic skill documents which components are deprecated and their
replacements. Existing usages SHOULD be migrated when the surrounding code is
being modified.

**Rationale:** a shared component library guarantees visual consistency,
reduces duplication, and centralizes accessibility fixes. Versioned
consumption gives a predictable upgrade path, and blocking new usages of
deprecated components limits future migration scope.

### XVI. Styling, BEM, and Design Tokens

CSS selectors MUST use classes only; IDs MUST be reserved for JavaScript
targeting when no alternative exists. Nested selectors SHOULD be avoided to
preserve specificity control and readability.

Class names MUST follow BEM. Blocks MUST be independent components
(`.button`). Elements MUST be parts of a block and use double underscores
(`.button__text`). Modifiers MUST represent variations and use double hyphens
(`.button--large`). Elements MUST NOT be nested in class names
(`.block__elem`, not `.block__elem1__elem2`).

Color, typography, spacing, shadow, and radius values MUST reference design
tokens, not raw values. Semantic tokens MUST be preferred over primitive
tokens when styling UI surfaces. Tokens MUST NOT be invented; only tokens
documented by Unnnic are valid. In this repository, Unnnic SCSS tokens are
injected into every SCSS block (`@use '@weni/unnnic-system/src/assets/scss/unnnic.scss'`).
Spacing MUST use the `$unnnic-space-{n}` scale; the deprecated
`$unnnic-spacing-*` tokens and the `inset` / `inline` / `stack` / `squish`
aliases MUST NOT be used.

**Rationale:** classes and flat BEM names give scoped, collision-free CSS that
scales across teams and avoids specificity wars. Tokens decouple design
decisions from implementation, enable global visual changes, and keep a
single source of truth for the visual language.

### XVII. Microfrontend Isolation

This microfrontend MUST NOT pollute the global scope (`window`, document
styles). Styles MUST be scoped or prefixed to avoid collision with the host or
other microfrontends. Global event listeners MUST be cleaned up on unmount.

In this repository:

- PostCSS prefixes all styles with `.insights-webapp` (`postcss.prefix` in
  `rspack.config.mjs`), and `mountInsightsApp` adds that class to the mount
  container. Global stylesheets (`src/styles/global.scss`, `reset.scss`) MUST
  stay under that prefix.
- Unnnic overlays teleport into the mount container (`teleportTarget`), so
  modals and drawers stay inside the microfrontend boundary.
- Browser storage MUST go through `moduleStorage` (`src/utils/storage.js`),
  which namespaces keys with `insights_`.
- Global listeners SHOULD use `useEventListener` from `@vueuse/core`, which
  removes them automatically on unmount.

**Rationale:** isolation prevents cross-microfrontend interference and keeps
each module independently deployable and testable.

### XVIII. Host Communication Contract

This microfrontend MUST communicate with the host through a documented
contract (custom events, props, or a shared message bus). Direct DOM
manipulation of elements outside the microfrontend boundary MUST NOT occur.

The contract in this repository consists of the exposes listed in
Principle IV and the host's `connect/sharedStore`, read only through
`src/utils/hostSharedStore.js`. Remote modules MUST be loaded through
`safeImport` / `safeAsyncComponent` (`src/utils/moduleFederation.js`), which
report failures to Sentry and degrade gracefully when the app runs standalone
(no `MODULE_FEDERATION_CONNECT_URL`). Tests MUST use the mock at
`tests/__mocks__/connect/sharedStore.js` instead of a real host.

**Rationale:** explicit contracts make integration predictable and let host
and module evolve independently. DOM encapsulation prevents fragile coupling.

### XIX. State Management

Global state MUST be managed through Pinia stores in `src/store/modules/`.
State MUST NOT be duplicated across components or stores. Related state
SHOULD be grouped in logical modules (e.g., `humanSupport/`,
`conversational/`). Local component state SHOULD be preferred when the data
does not need to be shared.

**Rationale:** centralized, non-duplicated state prevents synchronization bugs
and makes data flow traceable. Modular stores mirror feature boundaries and
simplify testing.

### XX. Async State Correctness

Async operations MUST track loading, success, and error states consistently.
Silent failures MUST NOT occur; errors MUST be surfaced to the user or logged
for debugging. Contradictory states (e.g., loading and error simultaneously)
MUST be prevented. Double submissions MUST be guarded against. State MUST be
rolled back when an operation fails after an optimistic update.

**Rationale:** incorrect async state is one of the most common sources of bugs
and broken UX. Users must always know what is happening and never be left in
limbo.

### XXI. API Integration and Data Boundaries

API calls MUST be encapsulated in dedicated service modules separate from
components: in this repository, `src/services/api/resources/`, built on the
HTTP clients in `src/services/api/` (`http.js`, `chatsHttp.js`, `nexusHttp.js`,
`weniHttp.js`). Components MUST NOT call HTTP clients directly. Error handling
MUST be explicit; API errors MUST NOT surface as unhandled exceptions. Loading
and error states MUST be tracked and reflected in the UI.

Backend contracts MUST remain at the API/service boundary. Internal code MUST
use camelCase; snake_case fields from the backend MUST be normalized at the
adapter layer (service resources or `src/models/`). Raw backend fields MUST
NOT leak into stores, business logic, or components. DTOs or raw API
interfaces that intentionally represent the backend contract MAY use the
backend naming convention.

**Rationale:** separating API logic from presentation enables reuse,
simplifies testing, and keeps components focused on rendering. Normalizing at
the edge decouples the frontend from backend implementation details.

### XXII. Internationalization

User-facing strings MUST NOT be hardcoded; they MUST be externalized to locale
files through `vue-i18n` (`src/utils/plugins/i18n.js`). Date, number, and
currency formatting MUST respect the user's locale (`date-fns` locales,
`src/utils/numbers.ts`, `src/utils/currency.ts`, ICU messages via
`src/utils/icuMessageCompiler.js`). Locale files SHOULD keep parity across
all supported languages. New strings introduced in a PR MUST be localized
before merge.

Supported locales are `src/locales/en.json` (Crowdin source), `es.json`,
`pt_br.json`, and `ro.json`, currently at full key parity. Crowdin
upload/download workflows sync translations, and merged PRs that touch
`src/locales/**` open a Localization review ticket automatically.

**Rationale:** externalized strings enable translation without code changes.
Locale-aware formatting prevents confusion and builds trust with
international users.

### XXIII. Testing

Components with business logic MUST have unit tests. Test files MUST be
colocated with the code they test in a `__tests__/` subdirectory. Tests MUST
NOT depend on implementation details; they MUST verify behavior and outcomes.
Tests MUST NOT be added solely to increase coverage; they MUST validate real
user behavior. A test that would still pass after a regression is introduced
MUST be fixed or removed.

The stack is Vitest with `@vue/test-utils`, `@pinia/testing`, and jsdom
(`vitest.config.js`, `setupVitest.js`, helpers in `tests/utils/`). CI runs
`npm run test:coverage` and uploads results to Codecov.

**Rationale:** colocated tests are easier to maintain and discover.
Behavior-focused tests survive refactors; implementation-coupled tests become
liabilities, and tests that cannot catch real bugs give false confidence.

### XXIV. Performance

Unused dependencies MUST be removed. Heavy computations MUST be memoized or
debounced when executed on frequent events. Assets MUST be optimized (images,
fonts). Bundle size impact SHOULD be considered before adding new
dependencies, using `npm run analyze`. Initial load SHOULD prioritize
above-the-fold content.

**Rationale:** frontend performance directly affects user experience. Lean
bundles matter more for a microfrontend because its payload adds to the
host's load time.

### XXV. Defensive Programming and Maintainability

Defensive guards (null checks, fallback branches, runtime assertions) SHOULD
only be added when the invalid state is realistically reachable. Root causes
MUST be fixed rather than masked with defensive code. Guards MUST follow the
patterns already established in the surrounding code.

Business rules MUST NOT be duplicated across multiple locations; they MUST be
centralized in a single source of truth. Local duplication of utility code MAY
exist when extraction would create unnecessary coupling. Abstractions SHOULD
only be created when there is a clear pattern across multiple use cases.

**Rationale:** unnecessary guards obscure real logic, while fixing root causes
produces more robust code. Centralizing business rules prevents divergence;
tolerating incidental duplication avoids premature abstraction that couples
unrelated code.

## Technology Stack and Project Layout

- **Framework:** Vue 3.5 (Composition API), Pinia 3, Vue Router 4, vue-i18n 10.
- **Build:** Rspack through `@weni/rspack-config` (`rspack.config.mjs`), with
  Module Federation (`name: 'insights'`, remote `connect`). `vite.config.js`
  exists only to back Vitest.
- **UI:** `@weni/unnnic-system` with SCSS; charts with Chart.js.
- **Quality:** ESLint (`@weni/eslint-config/vue3`) with Prettier; Vitest with
  istanbul coverage.
- **Observability:** Sentry (`@sentry/vue`, `@sentry/browser`).
- **Runtime:** Node 24 in CI; production served by nginx from
  `docker/Dockerfile`.
- **Layout:** `src/components/` (UI by feature), `src/views/` (routed pages),
  `src/layouts/`, `src/store/modules/` (Pinia), `src/services/api/` (HTTP
  clients and resources), `src/models/` (domain models and types),
  `src/composables/`, `src/utils/`, `src/locales/`, `src/styles/`; shared test
  helpers and mocks in `tests/`; feature specs in `specs/`.

## Development Workflow and Quality Gates

1. Each feature starts from an engineering spec in `specs/<NNN-feature>/` that
   opens with the inheritance section (Principle V).
2. `plan.md` MUST pass the Constitution Check against every MUST in this
   document before research and again after design; any accepted violation
   MUST be justified in the plan's Complexity Tracking table.
3. Work lands through a pull request reviewed by CODEOWNERS (Principle I) with
   Conventional Commits (Principle VII).
4. CI (`.github/workflows/test-and-build.yml`) MUST pass `npm ci`,
   `npm run lint`, `npm run test:coverage`, and `npm run build`.
5. Releases are git tags: `X.Y.Z-develop` and `X.Y.Z-staging` deploy to their
   environments, and `X.Y.Z` deploys to production
   (`.github/workflows/build-insights-webapp-push-tag-shared.yaml`).

## Governance

This constitution supersedes other engineering practices for this repository.
Where it conflicts with a README, wiki, or habit, this document wins until it
is amended.

- **Precedence:** engineering base > frontend and frontend platform bases >
  project adaptation. A project exception MUST live inside the principle it
  modifies, with an explicit justification (see Principle XII); a base rule
  MUST NOT be weakened any other way.
- **Amendments:** changes are made by pull request to
  `.specify/memory/constitution.md`, updating the Sync Impact Report and the
  version line. Changes to the shared bases belong in
  `weni-ai/vtex-cx-engineering-constitutions`, not here; re-run
  `setup-engineering` to pull them in, preserving project exceptions that
  still apply.
